The supervisor runs only as PID1 in sudo unshare --mount --pid --fork
--mount-proc. It never writes the host PID allocator. The normal ancestry audit
logger pauses after reading unrelated target T's PPID, then the supervisor
reaps that parent and forces its numeric PID for a child of the actual adapter
worker. It retries until that replacement and T have equal creation ticks.
It requires Capture rejection and actual T survival. No production test hook
or private kernel API is used.

The fix retains pidfds for all resolved Linux parents through final chain
validation, in addition to the already retained target pidfd. Poll plus signal
zero reject exit/reuse, including zombies. Every PPID is reread after resolving
its pinned parent and again across the final chain. Equal parent/child creation
ticks, changed relationships and metadata/kernel failures reject admission.
Only the retained target pidfd can signal the target; no numeric-PID signaling
fallback was introduced. Ancestry pidfds are released on every outcome.

Limits remain explicit
----------------------
Hosted managed-overlay proof is SKIP on unproven configurations, not a managed
inspection pass. No managed source breakpoint, stepping, exception-control,
func-eval, device, real attach/restart or broader platform parity is claimed.
Windows retained-handle/Toolhelp behavior is unchanged. macOS has no independent
kernel-bound orphan cleanup; its negative contracts require target survival
and release their own fixture. Linux equal-tick ancestry may conservatively
decline independent cleanup for a legitimate launch.

The separately suggested Linux post-signal EINTR budget and Windows
TerminateProcess access-denied exit-race changes are deferred: deterministic
fault-path red proofs were not established within this bounded change.
